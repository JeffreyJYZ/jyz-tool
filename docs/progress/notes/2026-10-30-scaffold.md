# 2026-10-30 — scaffold

First commit of code. Version `0.1.0-alpha.1` on all four manifests. Nothing is implemented beyond a CLI shell and an empty desktop window; this note records what exists, what was measured, and what bit.

## Shape

```
package.json          bun workspace, private, scripts below
bunfig.toml           [fmt] useTabs, tabWidth 4, printWidth 100
biome.json            formatter tabs/4/100, linter preset recommended, docs excluded
tsconfig.json         ESNext, bundler resolution, types ["bun"], resolveJsonModule
.prettierignore       docs/ and local/ — bun fmt reads it
scripts/release.ts    build + publish artefacts
packages/core         @jyz/core, exports ./src/index.ts, VERSION from its package.json
packages/cli          jyz bin -> src/bin.ts, built on cac 7
packages/desktop      @jyz/desktop, Tauri 2 shell, static ui/index.html
.github/workflows     ci.yml (3-OS gates), release.yml (tag -> release)
```

## Scripts

- `bun run jyz` — help, from `packages/cli/src/bin.ts`.
- `bun run jyz --version` — `jyz/0.1.0-alpha.1 darwin-arm64 bun-v26.3.0`.
- `bun run typecheck` — `bun check`.
- `bun run lint` — `biome check .`.
- `bun run format:check` — `bun fmt --check`.
- `bun run test` — `bun test`, no tests yet.

Deliberately not named `check` or `fmt`: both would shadow Bun builtins, so `bun fmt --check` would write instead of verifying and `bun check` would stop typechecking.

## CLI

`cac` 7.1.0. `cac("jyz")`, then `cli.version(VERSION)`, `cli.help()`, and a bare invocation calls `cli.outputHelp()` because no command is registered yet. The bin carries a bun shebang, so `bun link` inside `packages/cli` yields a working `jyz` with no build step; compiled binaries come from `bun build --compile --target=bun-<platform>`.

`VERSION` is imported from `packages/core/package.json`, so the number has one home. Bumping requires all four manifests together — root, core, cli, desktop — plus `packages/desktop/src-tauri/tauri.conf.json` and `Cargo.toml`, which carry their own copy.

## Desktop

Tauri 2 shell, no frontend bundler: `build.frontendDist` points at `packages/desktop/ui`, a single static `index.html` with a dark page. `src-tauri/` holds `Cargo.toml` (`jyz-desktop`, lib `jyz_desktop_lib`), `build.rs`, `main.rs`, `lib.rs`, `tauri.conf.json`, and an empty capability set (`core:default` only, no commands exposed).

The icon is a hand-written SVG, `packages/desktop/app-icon.svg`: rounded dark square, hairline inner stroke, a geometric `j` in an off-white gradient, and a diamond dot instead of a circle. `bunx tauri icon` derives the platform set (icns, ico, Android and iOS variants) from it, so regenerate rather than editing derived files.

## Release

`scripts/release.ts` builds into `dist/release`:

- `core-<version>.tgz` — core package source
- `cli-<version>-<os>-<arch>[.exe]` — compiled binaries, five targets, cross-compiled from any host
- `desktop-<version>-<os>-<arch>.<ext>` — Tauri installers collected from `src-tauri/target/release/bundle`, extensions dmg/deb/AppImage/rpm/msi/exe

Flags: `--all` (every CLI target), `--no-cli`, `--no-desktop`, `--publish`, `--publish-only`. Publishing is idempotent: an existing tag gets `gh release upload --clobber`, otherwise `gh release create --prerelease`.

`release.yml` runs on `v*` tags and dispatches: a CLI job on Ubuntu, a desktop matrix across macOS, Linux and Windows (with the webkit2gtk dependency set), then a publish job that merges the downloaded artefacts. Tauri cannot cross-build a bundle, which is why desktop installers only ever come from the matrix.

## Traps hit

- Biome resolved to 2.6.4, not the 2.5.15 the earlier notes assumed. The config schema and `rules.recommended` were both stale; `bunx biome migrate --write` fixed both and produced `rules.preset`.
- `bun fmt` formats Markdown at width 80 and would have reflowed every plan document. It reads `.prettierignore` by default, so `docs/` and `local/` are listed there.
- `bash echo "$?"` after a pipe reports the pipe's status, not the command's; the first gate runs looked green while `bun check` had failed with `Cannot find name 'process'`. The real fix was `types: ["bun"]` in the root tsconfig.
- `@types/bun` was installed but unused until that `types` entry existed, so a `process` reference failed typecheck while working at runtime.
